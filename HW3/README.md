# Business Travel Automation

Мультиагентная система автоматизации оформления командировок. Пользователь описывает задачу обычным текстом, система сопоставляет запрос с корпоративными регламентами, задаёт недостающие вопросы, строит план оформления, параллельно подбирает элементы поездки, предлагает альтернативы и выполняет оформление после явного подтверждения.

## Постановка задачи

В компании правила командировок не являются заранее зашитой фиксированной схемой. Они находятся в корпоративных инструкциях и регламентах, могут изменяться, иметь версии, даты действия, область применимости и исключения. Поэтому система должна использовать RAG для поиска нормативных фрагментов и детерминированный Policy Rules Engine для принятия решений.

Автоматизируемый процесс начинается со свободного запроса сотрудника, например: «Нужна поездка из Москвы в Берлин на три дня для встречи с клиентом в бюджете 180 000 рублей». Из запроса извлекаются известные параметры, после чего RAG находит действующие правила. Только на основе найденных правил определяется, каких данных не хватает: даты, cost center, цель, необходимость визы, класс билета, согласующий руководитель и т.д.

После ответов пользователя RAG-поиск и проверка полноты выполняются повторно. Затем система формирует policy decisions и план: обязательные согласования, типы услуг и параллельные поисковые задачи. Пользователь получает несколько сопоставимых вариантов с ценой, условиями возврата, сроком действия и ссылками на применённые правила. Финальное бронирование выполняется только после явного подтверждения.

Если билет или номер стали недоступны, истёк hold, изменилась цена или часть ресурсов уже забронирована, запускается перепланирование. При отмене оформленной поездки система получает условия отмены, показывает штрафы и ожидаемый возврат, после чего выполняет отмену по подтверждению пользователя.

## Роли

### Пользовательские роли

- **Сотрудник** — создаёт запрос, отвечает на уточнения, выбирает вариант, подтверждает покупку или отмену.
- **Руководитель** — согласует цель, сроки и бюджет по матрице полномочий.
- **Финансовый контролёр** — проверяет cost center, лимиты и финансовые последствия.
- **Travel manager** — принимает ручные решения по исключениям и нестандартным случаям.
- **Администратор политик** — публикует и архивирует версии инструкций и регламентов.

### Роли мультиагентной системы

- **Request Parser Agent** — преобразует свободный текст в типизированный `TripRequest`.
- **Clarification Agent** — формирует вопросы по отсутствующим или неоднозначным полям.
- **Transport Search Agent** — ищет авиа- и железнодорожные билеты.
- **Hotel Search Agent** — подбирает размещение с учётом лимитов и отмены.
- **Transfer Search Agent** — подбирает трансфер и проверяет стыковки.
- **Visa & Insurance Agent** — определяет необходимость визы и страхования.
- **Booking Agent** — координирует выбранные offers и повторную проверку перед покупкой.
- **Cancellation & Refund Agent** — подготавливает отмену и контролирует возврат.
- **Replanning Agent** — классифицирует ошибки и выбирает новый маршрут процесса.
- **Supervisor Agent** — маршрутизирует этапы и специализированных агентов.
- **Summary Agent** — формирует объяснение результата.

Агенты не имеют прямого доступа к платёжным операциям. Поиск является агентной задачей, а hold, book, cancel, refund, идемпотентность и компенсации выполняются детерминированными операционными сервисами.

## Архитектурный обзор

Система состоит из следующих основных частей:

1. **Employee Portal / Travel API** — веб-интерфейс и API для текстового запроса, уточнений, согласований, выбора и подтверждений.
2. **LangGraph Orchestrator** — stateful workflow с checkpoint, human-in-the-loop, fan-out/fan-in и маршрутизацией перепланирования.
3. **Policy Knowledge & Decision Service** — отдельная RAG-подсистема и детерминированная проверка политик.
4. **Travel Agent Workers** — специализированные агенты поиска, бронирования, отмены и перепланирования.
5. **Booking & Compensation Service** — идемпотентные hold/book/status/cancel/refund и Saga-компенсации.
6. **Trip Case & Audit Store** — состояние кейса, policy snapshot, альтернативы, согласования, брони и аудит.
7. **LLM Gateway** — безопасный OpenAI-compatible клиент с отдельными конфигурациями parser/supervisor/worker/summary.
8. **Внешние системы** — корпоративный IAM, хранилище регламентов, поставщики билетов/отелей/трансферов, финансы, ЭДО и уведомления.

### RAG

RAG имеет два независимых контура:

- **Ingestion вне конкретной командировки:** администратор публикует документ, ingestion извлекает текст, нормализует и разбивает его на chunks, создаёт embeddings, строит keyword/vector indexes, проверяет provenance и quality gates, затем публикует версию.
- **Runtime во время командировки:** система строит query из нормализованных данных поездки и контекста сотрудника, выполняет hybrid retrieval и reranking, собирает контекст с citations, после чего Policy Rules Engine проверяет ограничения.

Runtime сохраняет snapshot использованных chunks, `policy_id`, версию, пункт, citation и хэш. Если действующий контекст отсутствует или версии конфликтуют, автоматическое оформление блокируется и кейс передаётся на manual review.

## Текущая реализация

В проекте реализован каркас на LangGraph:

- `travel_system/state.py` — типизированные состояния `TripState`, `TripRequest`, `PolicyChunk`, `PolicyDecision` и `SearchTask`.
- `travel_system/graphs.py` — `StateGraph`, `Send`, `interrupt`, `MemorySaver`, intake/planning, booking и cancellation graphs.
- `travel_system/agents.py` — специализированные классы агентов и mock Travel Provider adapters.
- `travel_system/rag.py` — ingestion документов, chunks, provenance и runtime retrieval.
- `travel_system/llm.py` — OpenAI-compatible `ChatOpenAI` gateway для ролей моделей.
- `app.py` — HTTP API и web UI integration.
- `static/index.html` — простой пользовательский интерфейс.

## Ограничения и упрощения

1. **Векторный поиск пока заменён lexical retrieval.** SQLite хранит chunks и поле для embeddings, но реальные embeddings, pgvector/Qdrant и reranker ещё не подключены. Это упрощение для запуска без внешней инфраструктуры.
2. **RAG ingestion упрощён.** Документы принимаются через API и индексируются в SQLite; production-вариант должен читать корпоративное object storage, извлекать PDF/DOCX/HTML, сохранять provenance и запускать quality gates.
3. **Поставщики заменены mock adapters.** Реальных API авиакомпаний, РЖД, отелей, трансферов, платежей и webhook reconciliation нет.
4. **Бронирование демонстрационное.** Booking Agent и Cancellation Agent присутствуют в графах, но фактическая операция создаёт demo booking; нет реального hold TTL, оплаты, возврата и компенсационной Saga.
5. **LangGraph checkpointer — `MemorySaver`.** Состояние workflow теряется после перезапуска процесса. Для production нужен PostgreSQL checkpointer с `thread_id=case_id`.
6. **LLM используется частично.** Gateway и отдельные конфигурации ролей реализованы; без ключа граф работает в безопасном режиме уточнений. Полная LLM-маршрутизация supervisor, worker-агентов и summary требует подключения моделей и строгих output schemas.
7. **Согласования упрощены.** Веб-API содержит модель approval, но полноценные уведомления и callback-процессы руководителей пока не подключены.
8. **Безопасность прототипная.** Нужны OIDC/JWT, RBAC, secret manager, PII redaction, подпись webhook и аудит доступа. API key сейчас хранится в локальной SQLite-базе для демонстрации persistence.
9. **Планирование упрощено.** В графе создаются базовые search tasks; production должен учитывать календарь, сложные зависимости, SLA поставщиков, лимиты retry и policy-driven обязательность услуг.
10. **Параллельность требует production hardening.** `Send` используется для fan-out; необходимы durable queue, reducer/barrier, retry policy, дедупликация и обработка partial results.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python app.py
```

Откройте <http://127.0.0.1:8080>.

Конфигурация LLM сохраняется в `travel.db`. В интерфейсе доступны отдельные настройки для `parser`, `supervisor`, `worker` и `summary`: provider, base URL, модель и API key. Ключ не возвращается в frontend после сохранения.

## API прототипа

- `GET/POST /api/config` — чтение и сохранение конфигурации LLM.
- `POST /api/trips` — запуск intake/planning graph.
- `GET /api/trips/{case_id}` — получение checkpoint state.
- `POST /api/trips/{case_id}/answers` — resume после clarification interrupt.
- `POST /api/trips/{case_id}/selection` — запуск booking graph.
- `POST /api/trips/{case_id}/replan` — запуск replanning graph.
- `POST /api/trips/{case_id}/cancel` — запуск cancellation graph.
- `GET/POST /api/policies` — публикация и просмотр policy documents для RAG.
- `GET /api/health` — health check.
